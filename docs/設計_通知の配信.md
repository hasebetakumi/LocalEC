# 実装設計：通知の配信（U-30）

利用者側 2 本と運営画面に続く、フェーズ 1 の最後の未実装機能。予約確定・リマインド・店舗によるキャンセル／変更・新着を、プッシュ通知とメールで届ける。
これまでに `notifications` テーブルへ「誰に何を」記録するところまでは実装済み。この設計は、その記録を実際に届ける部分と、記録を作る残りの契機（確定・リマインド・新着）を扱う。

- 要件：`docs/要件定義_フェーズ1.md` U-30、A-11「公開時に新着通知を送るか」、A-12「変更を通知」、A-21「キャンセルを通知」
- データ：`design/DATA_MODEL.md` §8（種別・契機・配信の規則）
- 迷ったら 5 章（DB）と 6 章（送る処理）を正とする。どちらもローカルで検証済み

## 0. 着手手順（実装者向け）

1. `CLAUDE.md`、`app/AGENTS.md`、この文書を読む
2. 検証済みの部品はすでに置いてある：`app/supabase/migrations/20261013000000_notifications_enum.sql`、`…000001_notifications.sql`、`app/supabase/functions/send-notifications/index.ts`、`app/supabase/functions/.env.example`

4. 10 章の順序で進める。配信を動かすには `npx supabase functions serve` を別の端末で動かしておく
5. 終える前に `npm run typecheck`、`npm run lint`、`npm run format:check`、`npm test`

## 1. 範囲

| 含める | 含めない（後続・外部待ち） |
| --- | --- |
| 通知を作る契機の残り：予約確定、前日・当日のリマインド、公開時の新着 | プッシュの実機受信の確認（開発ビルドと Apple／Google の認証情報が要る） |
| 送る処理（Edge Function）：プッシュ（Expo Push API）とメール（SMTP）、再送、無効な端末の除外 | 本番のメール送信サービスの契約・ドメイン認証 |
| アプリ側：端末の登録、通知の許可、タップで該当画面を開く、通知オフの反映、ログアウト時の解除 | 通知の種類ごとの設定（要件でフェーズ 2） |
| 定期実行（pg_cron）と送る処理の呼び出し（pg_net）、Vault の設定 | アプリ内の通知一覧画面（設計資料にない） |
| ローカルでの一気通貫の確認（Mailpit） | プッシュ受領の確認（receipts）。任意で 11 章 |

## 2. 全体の流れ

```
契機（DB のトリガー／定期実行）
  └─ notifications に行を作る（title・body・宛先・種類。すでに実装済みの契機：店舗キャンセル・期間変更）
        └─ 取引通知なら insert トリガーで即時に、それ以外は毎分の pg_cron で
              └─ pg_net → Edge Function send-notifications（x-cron-secret で呼び出し元を確認）
                    ├─ claim_notifications()：未送信を 100 件まで取り出す（同時実行でも二重に取らない）
                    ├─ プッシュ：push_tokens の端末へ Expo Push API（100 件ずつ）。DeviceNotRegistered なら端末を無効化
                    └─ メール：profiles.email へ SMTP（nodemailer）。ローカルは Mailpit、本番は送信サービスの SMTP
```

| 種類 | 契機 | 宛先 | プッシュ | メール |
| --- | --- | --- | --- | --- |
| `booking_confirmed` | `bookings` の insert（新規） | 予約した本人 | ○ | ○ |
| `reminder` | 前日 18:00・当日 8:00（日本時間）の定期実行（新規） | 予約中の本人 | ○ | ○ |
| `cancelled_by_staff` | `staff_cancel_booking`（実装済み） | 本人 | ○ | ○ |
| `listing_changed` | `listings_guard_update`（実装済み） | 予約中の人 | ○ | ○ |
| `listing_published` | 公開時（`notify_on_publish` が ON）の定期実行（新規・種類を追加） | 通知オンで端末のある全員 | ○ | — |
| `notice_published` | 同上（お知らせ） | 同上 | ○ | — |

規則（DATA_MODEL §8）：`notifications_enabled = false` ならプッシュだけ止め、取引通知のメールは送る。新着（上 2 つ）はプッシュだけで、メールは送らない（判断：メールの新着配信は迷惑になりやすく、要件にもない）。

## 3. 判断した点（変更するならこの文書を先に直す）

1. **メールは SMTP で送る**。ローカルは Mailpit、本番は送信サービス（Resend・SendGrid・Amazon SES など SMTP を提供するもの）に接続先を変えるだけにする。サービスは未定（Q-02 と同様に先方と決める）。HTTP API に縛られないため
2. **送る処理は Edge Function 1 本**（`send-notifications`）。pg_cron ＋ pg_net から呼ぶ（Supabase 公式の定期実行の形）。取引通知は insert トリガーからも同じ関数を即時に呼び、確定通知が数秒で届くようにする
3. **呼び出し元の確認は 2 段**：Supabase の JWT 検証（publishable key）＋ `x-cron-secret` ヘッダー（Vault と関数の秘密が一致）。関数は service role で DB を読む
4. **新着はプッシュだけ、端末のある利用者にだけ作る**。全利用者に行を作らない（件数が膨らまない）
5. **リマインドは前日 18:00 と当日 8:00（日本時間）**。要件定義の未決事項 Q-01「リマインド時刻の既定値」の仮置き。pg_cron は UTC なので `0 9` と `0 23`
6. **再送は 5 回まで、間隔は 5 分 × 回数**。取り出した通知は 5 分で解放（関数が落ちても取り直せる）
7. **端末トークンは `push_tokens` に持ち、同じトークンは持ち主を付け替える**（家族で端末を共有しても最後にログインした人に届く）
8. **タップで開く画面**は関数側で決める：予約の通知 → `/bookings/<id>`、お知らせ → `/notices/<id>`、新着 → `/listings/<id>`
9. **Web はプッシュなし**（要件どおり）。マイページの通知スイッチも Web では出さない（実装済み）
10. **Android の Expo Go ではプッシュが使えない**（SDK 53 以降）。アプリは失敗しても画面を止めない。実機確認は開発ビルドで行う
11. **受領の確認（receipts）は任意**（11 章）。iOS で端末が外れた場合はチケットでは分からないため、入れると無効な端末が早く消える

## 4. アプリ側

### 4.1 追加するライブラリ・設定

- `npx expo install expo-notifications`
- `app.json` の plugins に `["expo-notifications", { "icon": "./assets/images/notification-icon.png", "color": "#B3471A", "defaultChannel": "default" }]`。アイコンは 96×96 の白い PNG（透過）を用意する（ロゴ案が決まるまでは買い物袋のアイコンで仮）
- Expo Go の Android ではプッシュを使えないので、実機確認は `eas build --profile development` の開発ビルドで行う

### 4.2 端末の登録（`src/features/notifications/push.ts`）

```ts
export async function registerForPush(): Promise<'registered' | 'denied' | 'unavailable'> {
  if (Platform.OS === 'web' || !Device.isDevice) return 'unavailable';   // シミュレータ・Web は対象外
  if (Platform.OS === 'android') {
    await Notifications.setNotificationChannelAsync('default', {
      name: 'お知らせ', importance: Notifications.AndroidImportance.DEFAULT,
    });
  }
  const { status: current } = await Notifications.getPermissionsAsync();
  const status = current === 'granted' ? current : (await Notifications.requestPermissionsAsync()).status;
  if (status !== 'granted') return 'denied';
  const projectId = Constants.expoConfig?.extra?.eas?.projectId;
  const { data: token } = await Notifications.getExpoPushTokenAsync({ projectId });
  await supabase.rpc('register_push_token', { p_token: token, p_platform: Platform.OS });
  return 'registered';
}
```

- `expo-device` は `Device.isDevice` のために入れる（Expo Go 同梱）
- 呼ぶタイミング：ログイン済みで `profile.notifications_enabled` のとき、アプリ起動時に 1 回（`AuthProvider` でプロフィールを読み終えた直後）。失敗（Expo Go の Android など）は握りつぶしてログだけ
- `getExpoPushTokenAsync` は `projectId` が必須。`app.json` の `extra.eas.projectId` をそのまま使う

### 4.3 通知オフ・ログアウト

- U-30 のスイッチをオン：`notifications_enabled = true` を保存してから `registerForPush()`。`denied` なら「端末の設定で通知を許可してください」の帯を出す（スイッチはオンのまま）
- オフ：`notifications_enabled = false` を保存するだけ。送る側がプッシュを止める。端末トークンは残す（再びオンにしたらすぐ届く）
- ログアウト：`push_tokens` から自分のトークンを消してから `signOut()`（`delete_push_token(p_token)` は不要。RLS で自分の行を直接 delete できる）
- アカウント削除：`profiles` の cascade で消える（実装済み）

### 4.4 受け取ったときの動き

- ルートの `_layout.tsx` で `Notifications.setNotificationHandler`：前面で受けたらバナーとリストに出す（`shouldShowBanner: true, shouldShowList: true, shouldPlaySound: false, shouldSetBadge: false`）
- タップ：`addNotificationResponseReceivedListener` と起動直後の `getLastNotificationResponseAsync` で `data.url` を取り、`router.push(url)`。未ログインなら `saveNextPath(url)` してログインへ。同じ通知を二度開かないよう `response.notification.request.identifier` を覚える
- 予約の詳細（`/bookings/<id>`）は既存の画面。お知らせ詳細を開いたら既読にする処理も既存

## 5. DB（`20261013000000_notifications_enum.sql`・`20261013000001_notifications.sql`）

### 5.1 方針

- **列挙型に `listing_published` を足す**。値の追加は同じトランザクションの中で使えないので、ファイルを分ける
- **`push_tokens`**：利用者 1 人に複数端末。`token` は一意。`disabled_at` で無効化（再登録で戻す）。RLS は自分の行だけ。登録は RPC `register_push_token`
- **`notifications` に配信の状態を足す**：`push_sent_at`／`push_ticket_id`／`push_error`、`email_sent_at`／`email_error`、`attempts`、`next_attempt_at`、`claimed_at`、`dedupe_key`（リマインドと新着の二重作成を防ぐ一意キー）
- **`push_error = 'done'`** は「送らないで確定」（通知オフ・端末なし・端末が外れた）。未送信と区別するための印
- **契機**：`bookings` の insert トリガー（確定）、`emit_reminders('day_before'|'same_day')`、`emit_publish_notifications()`（`listings.publish_notified_at` で一度だけ）
- **取り出し**：`claim_notifications(p_limit)`。`for update skip locked` で同時実行に耐える。5 回失敗した通知は取り出さない
- **呼び出し**：`invoke_send_notifications()` が Vault の `functions_url`・`publishable_key`・`cron_secret` を読んで `net.http_post`。未設定なら何もしない（配信の準備ができるまで安全）
- **定期実行**：毎分の送信、10 分ごとの新着、リマインド 2 本

### 5.2 検証済み（2026-10-10、ローカル Supabase）

ロールバック付きの SQL で確認：端末の登録と二重登録の上書き、利用者には自分の端末だけ見える、予約で確定通知ができる、利用者は `claim`／`emit` を呼べない、リマインドが当日・前日で 1 件ずつでき二度目は 0、新着は端末のある利用者にだけでき二度目は 0、取り出しで取引通知はメール対象・新着は対象外、二度目の取り出しは空、5 回失敗で取り出されない、定期実行 4 本の登録、Vault 未設定なら呼び出しが null。
さらに Vault を設定した状態で一気通貫：予約 → トリガー → pg_net → 関数が 1 件取り出し → 偽の端末は `DeviceNotRegistered` で無効化（`push_error = done`）→ メールが Mailpit に届く（件名「【LocalEC】予約が完了しました」）。秘密なしの呼び出しは拒否。

SQL の全文は上記 2 ファイル（この文書には写さない。食い違ったらファイルを正とする）。

## 6. 送る処理（`supabase/functions/send-notifications/index.ts`）

検証済みの実装が置いてある。要点：

- 入口：`x-cron-secret` が環境変数 `CRON_SECRET` と一致しなければ 403（JWT 検証は Supabase 側で先に行われ、無効なら 401）
- `SUPABASE_URL`・`SUPABASE_SERVICE_ROLE_KEY` は Supabase が自動で渡す。これで RLS を越えて `notifications`・`push_tokens`・`profiles` を読む
- `claim_notifications(100)` → プッシュ（`push_sent_at` が空で `push_error <> 'done'`）→ メール（`email_sent_at` が空で取引通知）
- プッシュ：通知オフか端末なしなら `done`。Expo Push API に 100 件ずつ。チケット `ok` → `push_sent_at`・`push_ticket_id`。`DeviceNotRegistered` → その端末を無効化し `done`。他のエラー → `push_error` と `next_attempt_at`
- メール：件名「【LocalEC】<title>」、本文は `body` ＋「アプリの『予約・申込』からも確認できます」＋送信専用の注記。削除済み・アドレスなしは `no_address` で送った扱い
- 環境変数：`CRON_SECRET`、`SMTP_HOST`／`SMTP_PORT`／`SMTP_SECURE`／`SMTP_USER`／`SMTP_PASS`、`MAIL_FROM`、任意で `EXPO_ACCESS_TOKEN`（`.env.example` 参照）

直すべき点（実装者向け）：本文の文面は 5 章のトリガー・関数（SQL）側で作っているので、文言の変更は SQL を直す。HTML メールにするなら `html` を足す（任意）。

- **関数の純粋な部分を `helpers.ts` に分けた**：`deepLink()`・`retryAt()`・`chunk()`・`emailContent()`・`EMAIL_KINDS`。Deno に依存しないので、アプリの Jest（`src/features/notifications/sendHelpers.test.ts`）でテストし、送る側のタップ先がアプリ側の `notificationUrl()` で開ける形かも確かめている
- **関数フォルダはアプリの型チェックと lint から外した**：`tsconfig.json` の `exclude` と `eslint.config.js` の `ignores` に `supabase/functions`。Deno の `npm:` 読み込みをアプリの tsc が解けないため
- **ローカルのメールは Mailpit の SMTP を外へ出して送る**：`config.toml` の `smtp_port = 58325`。関数のコンテナから `supabase_inbucket_localec` の名前が引けなかったので、`.env` は `SMTP_HOST=host.docker.internal`・`SMTP_PORT=58325`
- **退会で端末トークンも消す**：`delete_my_account()` を通知のマイグレーションで置き換え、`push_tokens` を削除。アプリ側も退会の前に `unregisterPush()` を呼ぶ
- **導入時点で公開済みの掲載は新着通知を送らない**：`publish_notified_at` を足したマイグレーションで、`publish_start <= now()` の掲載を通知済みにした。シードも同じ（公開予定の掲載だけが公開時刻に通知される）。入れないと初回の定期実行で全掲載の新着がまとめて届く
- **U-30 スイッチをオンにしたときにも端末を登録する**：起動時の登録に加え、オンにした瞬間に `registerForPush()`。端末側で拒否されていたら「端末の設定で、このアプリの通知を許可してください。」を出す
- **通知アイコンは仮**：`assets/images/notification-icon.png`（白い買い物袋、96×96、背景透過）。色は `#B3471A`
- **受領の確認（11 章）は `push_tickets` 表で入れた**：1 人が複数の端末を持つと 1 通知に複数のチケットが付き、通知の列 1 つでは外れた端末を特定できないため。送信で `ok` のチケットを端末トークンと一緒に記録し、毎分の実行の最後に 15 分以上前のものを 1000 件まで `getReceipts` に投げる。`DeviceNotRegistered` の端末を無効化し、受領が返ったものと 24 時間を過ぎたものを消す。表は RLS を有効にしてポリシーなし（サービスロールだけ）。振り分けは `classifyReceipts()`（`helpers.ts`）で Jest のテストあり。関数の応答は `{"claimed": n, "receipts": m}`

### 確認済み（ローカル）

- 予約 → トリガー → pg_net → 関数 → 偽トークンが `DeviceNotRegistered` で無効化 → Mailpit に確定メール（予約から 1 秒以内）
- 店舗キャンセル、前日リマインド、シードの確定メール
- 新着掲載：トークンがある利用者にだけ通知ができ、偽トークンの無効化後は `push_error='done'` で再送しない
- 関数の認証：JWT なしで 401、`x-cron-secret` なしで 403
- Web の書き出しにプッシュ登録のコードが入らない（`push.web.ts` が使われる）
- 受領の確認：実際の Expo API に投げ、24 時間を過ぎたチケットだけが消え、受領のないチケットは残る。利用者のロールからは `push_tickets` を読めない
- 4 つのチェック（typecheck・lint・format:check・test）

### 残った点

- **実機での受信は未確認**（10 章 C の「Expo Go の iOS で許可とトークン登録」と F）。Android の Expo Go は SDK 53 以降プッシュ不可なので、開発ビルドで確かめる
- 本番の Vault（`functions_url`・`publishable_key`・`cron_secret`）、関数の秘密（SMTP・`CRON_SECRET`）、メール送信サービスは 7 章の手順で設定する
