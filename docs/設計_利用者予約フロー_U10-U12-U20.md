# 実装設計：利用者の予約フロー（U-10 → U-12 → U-20）

design/ の画面設計（HTML プロトタイプ）と DATA_MODEL.md を、既存の Expo（React Native）+ Supabase 環境で再現するための設計。
対象は **最初の1本＝商品の予約フロー**（ホーム → 商品詳細 → 数量選択 → 予約完了）。DB スキーマはフェーズ1全体（イベント・求人・お知らせ・運営画面）を見越して定義する。

**実装状況（2026-10-10）**：この文書の範囲は実装済み（ブランチ `feature/user-booking-flow`）。実装中に設計から変えた点は「7. 実装で変えた点」にまとめ、本文もそれに合わせて更新した。

この文書だけで実装に着手できるように書いてある。迷ったら付録 A（画面寸法）と付録 B（SQL 全文）を正とし、それでも足りない点だけ design/ の HTML を見る。

- 画面の正：`design/01_利用者画面_閲覧.dc.html`、`design/02_利用者画面_予約とアカウント.dc.html`、`design/05_状態違い.dc.html`、`design/06_デザインルール.dc.html`
- データの正：`design/DATA_MODEL.md`
- 要件定義と設計資料が食い違う点は、設計資料（00 の決定事項 Q1〜Q25）を優先する。例：ログインは要件定義の「パスワード＋Apple サインイン」ではなく、Q2 の「パスワードなし・メールのマジックリンク」で作る（2026-10-10 に要件定義もこちらに更新済み）

## 0. 着手手順（実装者向け）

1. `CLAUDE.md`、`app/AGENTS.md`、この文書を読む
2. `app/` で `npm install` → `npx supabase start`（初回は Docker イメージ取得で数分）→ `npx supabase status` の値を `app/.env` に写す
3. 第 5 章の順序で進める。各ステップの完了条件を満たしてから次へ
4. 終える前に `app/` で `npm run typecheck`、`npm run lint`、`npm run format:check`、`npm test`
5. 画面の見た目は Web（`npm run web`）で design/screenshots と見比べる。Expo Go の実機確認はステップ 3 以降で行う（`EXPO_PUBLIC_SUPABASE_URL` を PC の IP にする）

Expo の API は記憶で書かず、`https://docs.expo.dev/versions/v57.0.0/` を確認する（`app/AGENTS.md`）。

- 一覧・詳細・予約・認証はタブの外（ルート Stack）に置く。タブバーを隠して全画面で出すため

- Expo Router の `typedRoutes` が有効なので、`router.push({ pathname: '/listings/[id]', params: { id } })` の形で書く

| --- | --- |

| その他 | 予約できませんでした。時間をおいてもう一度お試しください。 |

**U-01（最小構成）**
- 方式：マジックリンク（`signInWithOtp`）。ログインと新規登録はどちらも同じ `signInWithOtp` を呼び、違いはメタデータの有無だけ。詳細は付録 C
- ログイン：メール入力 →「ログイン用リンクを送る」→ `auth/sent`。「新規登録」→ `auth/register`。「ログインせずに商品を見る」→ `router.back()`
- 新規登録：氏名・電話・メール・規約同意。同意するまで「登録する」は無効。送信時に `options.data = { name, phone, agreed_terms_at }` を渡す
- `?complete=1` モード（メールだけでログインしたが登録情報がない人）：同じフォームでメール欄を非表示にし、「登録する」で `profiles` を直接 update（RLS で自分の行）。完了後に保存していた `next` へ
- メール送信後：宛先表示、「メールを再送する」は同じ引数で `signInWithOtp` を再実行（Supabase のレート制限により 60 秒以内は失敗するので、失敗時は「しばらく待ってから再送してください」）
- 電話番号：ハイフン・空白を除いて保存。`^0\d{9,10}$` に合わなければ欄の下に赤字「電話番号を正しく入力してください」
- `next` の保存先：`AsyncStorage` のキー `auth.next`（Web は同じ API で localStorage に落ちる）。`auth/confirm` が消費する

## 3. DB 設計（Supabase / PostgreSQL 17）

マイグレーションは `app/supabase/migrations/20261010000000_initial.sql` に付録 B の SQL をそのまま置き、`npx supabase db reset` で再現する。型は `npm run gen:types`（`supabase gen types typescript --local` ＋ Prettier）で `src/lib/database.types.ts` に生成し、手書きしない。スキーマを変えたら `npm run db:reset` → `npm run gen:types`。

### 3.1 方針

- **listings は単一テーブル**。種類別の列は nullable、必須は種類ごとの CHECK で担保。ホーム・A-11・A-20 が種類をまたいで並べるため JOIN なしで読める
- **掲載状態は DB では 3 値**（draft / published / ended）。「公開予定」は `publish_start > now()` から導出し、表示用の 4 値はビュー `listing_availability.display_status` が返す。時刻到来時の自動更新ジョブが不要になる
- **残数はビューで集計**（`reserved + completed` の合計）。集計そのものは security definer 関数 `listing_reserved_quantities()` で行う。bookings は RLS で自分の分しか見えないため、ビューで直接集計すると他人の予約が漏れて残数が多く見える（実装時に発見して修正）。バッジ・売り切れ判定はアプリ側の純関数
- **採番は 1 行のカウンターを `for update` でロック**し、`reserved` 限定の部分ユニークインデックスで「同じ番号が同時に reserved で存在しない」を保証
- **予約の確定は RPC `create_booking` 内で listings 行をロック**して直列化。失敗はコード文字列（`sold_out` など）を `raise exception` で返す
- **profiles は auth.users の insert トリガーで作る**。マジックリンクだけでログインした人は name/phone が空で作られ、アプリ側で「登録情報の入力」に誘導する（付録 C）
- 通知は `notifications` テーブルだけ作り、配信は後続

### 3.2 エンティティ（詳細は付録 B）

| テーブル | 役割 |
| --- | --- |
| `profiles` | 利用者・スタッフ共通。`auth.users` と 1:1 |
| `stores` | 店舗。`payment_methods` は enum 配列 |
| `store_staff` | スタッフの所属（複数店舗可） |
| `listings` | 掲載（product / event / job / notice） |
| `bookings` | 予約・申し込み・応募。`number` 4桁、`store_id`・`kind` を非正規化 |
| `booking_number_counter` | 採番用 1 行 |
| `notifications` | 通知の記録（配信は後続） |
| ビュー `listing_availability` | listings ＋ `reserved_quantity`・`remaining`・`display_status` |
| 関数 `listing_reserved_quantities()` | 掲載ごとの予約数（RLS を通さず全員分を数える。返すのは掲載 ID と数量だけ） |

### 3.3 RLS の要点

| テーブル | anon / 利用者 | スタッフ |
| --- | --- | --- |
| stores | select 可 | 所属店舗を update |
| listings | select：`(status='published' and publish_start <= now()) or status='ended'`。draft と公開予定は見えない | 所属店舗の行を全操作 |
| bookings | select：`user_id = auth.uid()`。insert は RPC 経由のみ | 所属店舗の行を select / update |
| profiles | select / update：`id = auth.uid()` | 自店舗の予約者分を select |
| booking_number_counter | なし（RPC のみ） | なし |
| notifications | select / update：自分の分 | なし |

スタッフ判定は関数 `is_store_staff(store_id)`。

## 6. 判断した点（変更するならこの文書を先に直す）

1. listings は単一テーブル
2. 掲載状態は DB では 3 値、「公開予定」は導出
3. 採番はカウンター行のロック ＋ reserved 限定ユニークインデックス
4. 残数の最終判定は RPC 内の行ロック
5. U-01 を最小構成で含める。ログインと新規登録は同じ `signInWithOtp`、登録情報の有無で後から分岐
6. 追加ライブラリは TanStack Query と react-native-svg の 2 つ
7. 数量の単位（食／袋／個／本）は DATA_MODEL にないので `listings.unit`（既定「食」）を追加。A-10 の入力項目にも足す
8. 期限切れ（expired）の自動遷移と通知の配信は含めない。テーブルと列だけ用意
9. 「予約へ進む」からの戻り先は `AsyncStorage` に保存（メールのリンク URL には載せない）

## 7. 実装で変えた点・残った点

### 変えた点

| 項目 | 設計時 | 実装 | 理由 |
| --- | --- | --- | --- |
| 残数の集計 | ビュー内で bookings を直接集計 | security definer 関数 `listing_reserved_quantities()` 経由 | RLS で他人の予約が見えず、残数が多く出ていた |

| マジックリンクの有効期限 | 既定（1 時間） | 15 分（`otp_expiry = 900`） | U-01 の画面文言に合わせた |
| メールテンプレート | magic_link のみ | magic_link と confirmation の両方 | 新規ユーザーには confirmation が使われる |
| Supabase クライアント | 型なし | `createClient<Database>` | 型なしだと取得結果が any で、型チェックが効いていなかった |

-- 他人の予約が漏れて残数が多く見える。集計だけを security definer で行い、
-- 返すのは掲載 ID と数量だけにする（個人情報は出さない）
create function public.listing_reserved_quantities()
returns table (listing_id uuid, reserved_quantity integer)
language sql stable security definer set search_path = public as $$
  select b.listing_id, sum(b.quantity)::integer
  from public.bookings b
  where b.status in ('reserved', 'completed')
  group by b.listing_id;
$$;

-- ビュー：残数と表示状態 ----------------------------------------
-- security_invoker なので listings の RLS（下書き・公開予定を隠す）はそのまま効く
create view public.listing_availability
with (security_invoker = on) as
select
  l.*,
  coalesce(b.reserved_quantity, 0)::integer as reserved_quantity,
  case
    when l.kind = 'product' then l.quantity_total - coalesce(b.reserved_quantity, 0)
    when l.kind = 'event'   then l.capacity       - coalesce(b.reserved_quantity, 0)
    else null
  end::integer as remaining,
  case
    when l.status = 'draft' then 'draft'
    when l.status = 'ended' or l.publish_end <= now() then 'ended'
    when l.publish_start > now() then 'scheduled'
    else 'published'
  end as display_status
from public.listings l
left join public.listing_reserved_quantities() b on b.listing_id = l.id;

create function public.next_booking_number() returns text
language plpgsql as $$
declare
  v_last      integer;
  v_candidate integer;
  v_number    text;
  v_i         integer;
begin
  select last into v_last from public.booking_number_counter where id = 1 for update;
  for v_i in 1..9999 loop
    v_candidate := (v_last + v_i - 1) % 9999 + 1;   -- 1..9999、9999 の次は 1
    v_number := lpad(v_candidate::text, 4, '0');
    if not exists (select 1 from public.bookings where number = v_number and status = 'reserved') then
      update public.booking_number_counter set last = v_candidate where id = 1;
      return v_number;
    end if;
  end loop;
  raise exception using message = 'no_number_available', errcode = 'P0001';
end $$;

-- 予約の作成 ----------------------------------------------------
create function public.create_booking(p_listing_id uuid, p_quantity integer)
returns public.bookings
language plpgsql security definer set search_path = public as $$
declare
  v_uid      uuid := auth.uid();
  v_profile  public.profiles%rowtype;
  v_listing  public.listings%rowtype;
  v_reserved integer;
  v_remaining integer;
  v_amount   integer;
  v_booking  public.bookings%rowtype;
begin
  if v_uid is null then
    raise exception using message = 'not_authenticated', errcode = 'P0001';
  end if;

  select * into v_profile from public.profiles where id = v_uid;
  if not found or v_profile.deleted_at is not null or v_profile.name = '' or v_profile.phone = '' then
    raise exception using message = 'profile_incomplete', errcode = 'P0001';
  end if;

  if p_quantity is null or p_quantity < 1 then
    raise exception using message = 'invalid_quantity', errcode = 'P0001';
  end if;

  -- 残数の競合を直列化
  select * into v_listing from public.listings where id = p_listing_id for update;
  if not found or v_listing.kind = 'notice' then
    raise exception using message = 'not_found', errcode = 'P0001';
  end if;
  if v_listing.status <> 'published' or v_listing.publish_start > now() or v_listing.publish_end <= now() then
    raise exception using message = 'not_published', errcode = 'P0001';
  end if;

  select coalesce(sum(quantity), 0) into v_reserved
  from public.bookings
  where listing_id = p_listing_id and status in ('reserved', 'completed');

  if v_listing.kind = 'product' then
    if v_listing.booking_deadline <= now() then
      raise exception using message = 'deadline_passed', errcode = 'P0001';
    end if;
    v_remaining := v_listing.quantity_total - v_reserved;
    if v_remaining < p_quantity then
      raise exception using message = 'sold_out', errcode = 'P0001';
    end if;
    v_amount := v_listing.price * p_quantity;

  elsif v_listing.kind = 'event' then
    if v_listing.application_deadline <= now() then
      raise exception using message = 'deadline_passed', errcode = 'P0001';
    end if;
    if p_quantity > v_listing.max_per_booking then
      raise exception using message = 'over_max_per_booking', errcode = 'P0001';
    end if;
    v_remaining := v_listing.capacity - v_reserved;
    if v_remaining < p_quantity then
      raise exception using message = 'sold_out', errcode = 'P0001';
    end if;
    v_amount := coalesce(v_listing.price_per_person, 0) * p_quantity;

  else -- job：人数到達でも締め切らない
    if v_listing.application_deadline <= now() then
      raise exception using message = 'deadline_passed', errcode = 'P0001';
    end if;
    if p_quantity <> 1 then
      raise exception using message = 'invalid_quantity', errcode = 'P0001';
    end if;
    v_amount := null;
  end if;

  insert into public.bookings (number, listing_id, store_id, user_id, kind, quantity, amount)
  values (public.next_booking_number(), v_listing.id, v_listing.store_id, v_uid, v_listing.kind, p_quantity, v_amount)
  returning * into v_booking;

  return v_booking;
end $$;

## 付録 C. 認証（マジックリンク）の具体手順

Supabase 公式ドキュメント（auth-email-passwordless、native-mobile-deep-linking）で確認した方式。`token_hash` 方式を採る。URL のフラグメントにトークンが乗らないので、Web・Expo Go・ビルド版で同じコードになる。

### C.1 config.toml の変更（`app/supabase/config.toml`）

```toml
[auth]
site_url = "http://localhost:8081"
additional_redirect_urls = ["http://localhost:8081/**", "localec://**", "exp://**"]

[auth.email.template.magic_link]
subject = "LocalEC ログイン用リンク"
content_path = "./supabase/templates/magic_link.html"
```

`app/supabase/templates/magic_link.html`：

```html
<h2>LocalEC にログイン</h2>
<p>下のリンクを押すとアプリに戻ってログインが完了します（有効期限 15 分）。</p>
<p><a href="{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=email">ログインする</a></p>
```

- `{{ .RedirectTo }}` には `signInWithOtp` の `emailRedirectTo` が入る。クエリは `?` で始めるので、`emailRedirectTo` にクエリを含めない
- 本番（Supabase ダッシュボード）でも同じテンプレートを Magic Link と Confirm signup の両方に設定する（新規ユーザーは signup テンプレートが使われる場合があるため、`[auth.email.template.confirmation]` にも同じ内容を指定しておく）
- 変更後は `npx supabase stop && npx supabase start` で反映

### C.2 送信（`features/auth/api.ts`）

```ts
import * as Linking from 'expo-linking';

const redirectTo = Linking.createURL('/auth/confirm');
// Expo Go: exp://192.168.x.x:8081/--/auth/confirm
// ビルド版: localec://auth/confirm
// Web:      http://localhost:8081/auth/confirm

export async function sendLoginLink(email: string) {
  return supabase.auth.signInWithOtp({ email, options: { emailRedirectTo: redirectTo } });
}

export async function sendRegisterLink(input: { email: string; name: string; phone: string }) {
  return supabase.auth.signInWithOtp({
    email: input.email,
    options: {
      emailRedirectTo: redirectTo,
      data: { name: input.name, phone: input.phone, agreed_terms_at: new Date().toISOString() },
    },
  });
}
```

`shouldCreateUser` は既定（true）のまま。既存ユーザーに `data` を渡しても無視されるだけなので、ログインと新規登録を同じ関数系で扱える。

### C.3 受け取り（`src/app/auth/confirm.tsx`）

```ts
const { token_hash, type } = useLocalSearchParams<{ token_hash?: string; type?: string }>();
useEffect(() => {
  if (!token_hash) return;
  supabase.auth.verifyOtp({ token_hash, type: 'email' }).then(async ({ error }) => {
    if (error) { router.replace('/auth/login?error=expired'); return; }
    const next = (await AsyncStorage.getItem('auth.next')) ?? '/(tabs)';
    await AsyncStorage.removeItem('auth.next');
    router.replace(next);   // AuthProvider が profile を読み、未完了なら register?complete=1 に振る
  });
}, [token_hash]);
```

- 画面はローディング表示だけ
- Web は `detectSessionInUrl: true` のままでよい（token_hash 方式では干渉しない）
- ネイティブで、アプリがすでに起動している状態でリンクを踏んだ場合も Expo Router が `/auth/confirm` にルーティングする。コールドスタートでも同じ

### C.4 AuthProvider

- `supabase.auth.getSession()` と `onAuthStateChange` で `session` を保持
- `session` があれば `profiles` を自分の id で読み、`profile` と `isRegistered = name !== '' && phone !== ''` を提供
- 公開する API：`{ session, profile, isRegistered, loading, signOut, refreshProfile }`

### C.5 ローカル確認

1. Mailpit：`http://localhost:58324`（`config.toml` の `[local_smtp] port`）
2. Web：ログイン画面でメール送信 → Mailpit でリンクをクリック → `http://localhost:8081/auth/confirm?token_hash=...` に戻る
3. Expo Go：`EXPO_PUBLIC_SUPABASE_URL` を PC の IP にする。Mailpit のリンク（`exp://192.168.x.x:8081/--/auth/confirm?...`）はスマホで開く必要があるので、リンクを QR にするか、スマホのブラウザで Mailpit（`http://<PC の IP>:58324`）を開いてタップする
4. レート制限：`[auth.rate_limit] email_sent = 2`（1時間あたり）が小さいので、開発中は `30` 程度に上げる
