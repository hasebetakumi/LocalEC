## 概要パート（1〜6枚目）

### 1. 表紙

- タイトル（仮）：「地域のお得情報が集まる地域EC」
- 宛先：アケボノ（柿沼さん）
- 提案者・日付

### 2. 提案の要点

- 何を作るか：アケボノ発の地域EC。余りもの・特産品・お得情報を地域の人に届けて売り切るアプリ
- なぜ今か
  - 職員・父兄・地域グループのネットワークがあり、「作れば作るほど売れる」状態。ネギ800本、じゃがいもも同様
  - 新米への切り替え時期など、季節ごとに大量に出るものがある
  - 余りものの情報が届かない機会損失
- どう進めるか：アケボノの自事業から始め、近隣事業者を加え、まずは関東3か所、その後10か所へ横展開
- 今後のアクション：進め方、分担、料金モデルの方向性

### 3. 課題とコンセプト

- 課題
  - 事業者側：余る前提で作らざるを得ない（パン屋・ケーキ屋はディスプレイを埋める必要がある、天候で余る、お弁当のロス）。作れば売れるのに、余りや大量収穫を知らせて売り切る手段がない
  - 生活者側：余りやタイムセールは店に行かないと分からず、帰りがけに寄れる機会を逃している
  - 地域側：お得情報、求人（脱穀の日払いなど）、検診、イベントがバラバラで、まとめて見る場所がない
  - 既存手段：LINEでの個別案内は登録の手間がある。TABETEは余りもの特化、楽天市場などは配送前提で手数料が高い
- コンセプト：「TABETEと楽天市場の間」。オンラインで予約し、直接取りに行く
- 軸は「お得」。お得がないと見てもらえないので、情報発信だけのアプリにはしない
- AIは噛まさず、情報とお得を確実に届けることに絞る

### 4. サービスの流れと主なユースケース

- 生活者：アプリを開く → 今日のお得を見る → 予約 → 帰りに受け取り
- 事業者：余りが出そう → 運営に情報を渡す → 掲載 → 予約状況を確認
- 代表ユースケース
  - 小川農園の通販と人手募集
  - カフェのお弁当余り
  - コインランドリーのキャンペーン

### 5. 展開ロードマップ

- フェーズ1：アケボノECとして開始。自事業の商品・情報のみ、現地決済
- フェーズ2：近隣のパン屋・ベーグル屋など事業者を追加、オンライン決済導入
- フェーズ3：横展開。保育園関係の知り合い先でまずは関東3か所、その後10か所程度
- 各フェーズの目安時期（予約システムのリリースが11月見込みであることを踏まえる）

### 6. 体制・料金・収益分配の方向性

- 共同開発方式：開発費を先にもらって納品して終わりではなく、一緒に育てて利益を分配する
- 分担
  - アケボノ側：事業・現場・事業者開拓・横展開の紹介
  - 開発側：設計・開発・運用保守
- 料金モデルの候補：事業者から月額／決済の一部／掲載のみ無料。運用しながら見直す
- 次のアクション：最初に載せる商品・情報の洗い出し、サンプルアプリ作成と試用、分配比率の決定

## 詳細パート（7枚目以降）

### 7. 背景の詳細

- 古米完売の経緯と、職員・父兄・地域グループのネットワークの強さ
- 現状はLINEで個別案内しており、登録の手間がある
- 箱物システムへの不満から予約システムを自前で作った経験

### 8. 課題の詳細

- 事業者側：パン屋・ケーキ屋はディスプレイを埋めるため作りすぎる、売り切る手段がない
- 生活者側：タイムセールを知らずに通り過ぎている
- 地域側：求人、検診、イベント、農作業の人手募集が集約されていない

### 9. ユースケース一覧

- 小川農園：米・野菜・うどん・ドレッシングの通販、脱穀などの日払い人手募集
- カフェ／キッチンカー：余ったお弁当の当日割引、50〜70食のロス削減
- コインランドリー：夏場閑散期に3,000円分カード先着30名などの配信
- 幼稚園・保育園：子ども向けイベント、検診、地域ニュース
- 近隣のパン屋・ケーキ屋：当日余り分の予約販売
- 将来：アルバイト募集、健康情報、近隣事業者の参加

### 10. 機能一覧（フェーズ1）

- 商品・お得情報の掲載（写真、価格、数量、受け取り場所・時間）
- 予約・取り置き
- 店頭受け取り・現地決済
- 通知（新着お得情報、フォロー店舗の投稿）
- 掲載情報の管理は運営側で行う（各事業者が直接入ると煩雑なため）
- 決済は後回し。GMO本番環境が整い次第カード等を追加

### 11. 画面イメージ・画面遷移

- ワイヤーフレーム1〜2枚
- 生活者側・事業者側それぞれの画面遷移図

### 12. 既存サービスとの比較

- TABETE：フードロス特化、決済手数料モデル、店舗月額なし
- 楽天市場など：配送前提、手数料が高い
- Shopifyなど：早く安く始められるが統合型の地域情報には向かない
- 本提案：地域限定、直接受け取り、余り以外の特産品・求人・イベントも載る統合型
- 参考事例：TABETEが東松山直売所の野菜を東上線で池袋へ運び、東松山価格で販売

### 13. 料金モデルの比較

- 3パターンの比較表：事業者月額／決済手数料／掲載無料＋一部有料
- 病院・検診など公共性の高い情報は無料枠とする考え方
- プラットフォームを持つ側に継続的に収益が入る構造を目指す
- 運用しながら課題が出たら変更する前提

### 14. ロードマップの詳細

- 各フェーズの対象事業者、機能、決済手段、目安時期を表にする
- 横展開候補：保育園関係の知り合い先、茨城の市場サイト関係者
- 既存予約システムの運用保守と1本契約にした場合の割安効果

### 15. 開発・運用体制

- 共同開発方式の狙い：変更のたびに見積もりで開発が停滞するのを避ける、小さい会社でも投資できる
- 役割分担の詳細表
- 運用フロー：情報収集 → 入力 → 掲載 → 予約対応 → 不具合対応

### 16. 収益分配・契約の考え方

- 利益分配の方式（比率は要相談）
- 横展開先からの収益の扱い
- 契約期間と見直しのタイミング

### 17. 概算スケジュール・費用

- 提案書承認 → 要件整理 → サンプルアプリ → 自事業でテスト運用 → 近隣事業者追加
- 初期費用の考え方（共同開発のため抑える）
- ランニング費用（サーバー等の実費）

### 18. リスクと対策

- 使われない：お得情報を必ず紐づけ、最初は自事業の確実なネタで運用
- 掲載の手間：運営側で入力代行、後で簡易入力を追加
- 決済トラブル：まず現地決済、本番環境が安定してからオンライン決済
- 横展開時の運用負荷：テンプレート化、地域ごとの運営者を置く

### 19. 次のアクション

- 合意事項の確認
- 最初に載せる商品・情報の洗い出し（小川農園、カフェ、コインランドリー）
- サンプルアプリの作成と試用
- 料金モデルと分配比率の決定
