## 2. DB 変更（`20261011000000_user_screens.sql`）

### 2.1 利用者のキャンセル `cancel_booking(p_booking_id uuid) returns bookings`

`security definer`。自分の予約だけ。1 トランザクションで行ロックして判定する。

| 判定 | エラーコード |
| --- | --- |
| 未ログイン | `not_authenticated` |
| 予約がない・他人の予約 | `not_found` |
| `status <> 'reserved'` | `not_cancellable` |
| 掲載の `cancel_deadline` が null | `cancel_not_allowed` |
| `cancel_deadline <= now()` | `cancel_deadline_passed` |

成功で `status='cancelled', cancelled_by='user', cancelled_at=now()`。残数はビューが `reserved + completed` だけを数えるので自動で戻る。

### 2.2 期限切れの自動処理 `expire_overdue_bookings()`

DATA_MODEL §6 の遷移「reserved → expired（商品：pickup_end 経過／イベント・求人：翌日 0:00）」を行う関数。

- 商品：`pickup_end <= now()`
- イベント：`event_end` の日本時間の翌日 0:00 を過ぎた
- 求人：`work_end` の日本時間の翌日 0:00 を過ぎた
- pg_cron で 10 分ごとに実行する（`cron.schedule('expire-overdue-bookings', '*/10 * * * *', ...)`）
- アプリの表示も同じ規則の純関数 `effectiveStatus()` で判定する。cron の実行間隔の間も表示がずれないようにするため

### 2.3 `profiles` の列権限（セキュリティ修正）

最初の 1 本の RLS は「自分の行は update 可」で、列を絞っていなかった。このままだと利用者が自分の `is_staff` や `deleted_at` を書き換えられる。

```sql
revoke update on public.profiles from authenticated, anon;
grant update (name, phone, notifications_enabled, agreed_terms_at) on public.profiles to authenticated;
```

### 2.4 メールアドレスの変更

- 変更はアプリから `supabase.auth.updateUser({ email }, { emailRedirectTo })`。新しいアドレスにだけ確認リンクを送る（design 02 の注記）。そのため `config.toml` の `double_confirm_changes = false`
- メールテンプレート `email_change` も token_hash 方式。`/auth/confirm?token_hash=…&type=email_change` で戻り、`verifyOtp({ type: 'email_change' })`
- 変更待ちのアドレスは `profiles.pending_email`。`auth.users.email_change` をトリガーで写す（既存トリガーを `update of email, email_change` に広げる）

### 2.5 アカウント削除 `delete_my_account()`

`security definer`。

1. 先に `expire_overdue_bookings()` を呼ぶ（期限を過ぎた予約は削除を妨げない。design 02 の注記）
2. 自分の `reserved` が 1 件でもあれば `has_active_bookings` で失敗
3. `profiles` を匿名化：`name=''`、`phone=''`、`email=''`、`pending_email=null`、`notifications_enabled=false`、`deleted_at=now()`
4. `delete from auth.users where id = auth.uid()`（セッション・ID 連携も auth 側で消える）

予約の記録を残すため、`profiles.id → auth.users.id` の外部キーを外す（auth のユーザーを消しても profiles と bookings は残る）。運営側は `deleted_at` を見て「削除済みユーザー」と表示する。

`phone` の CHECK は空文字を許しているので匿名化と両立する。

### 2.6 お知らせの既読

サーバーには持たず、端末（AsyncStorage）に既読の掲載 ID を持つ。

- ログインしていなくてもベルの未読数を出したいため
- 未読＝公開中のお知らせのうち、既読でなく、公開から 30 日以内のもの（古いお知らせを初回起動で全部 NEW にしない）
- 一覧を開いた時点では既読にしない。詳細を開いたら既読

DATA_MODEL §8 の notification（配信の記録）はプッシュ通知の実装時に使う。

## 3. 表示用の派生値（追加）

### 3.1 掲載（`features/listings`）

`Listing = Product | EventListing | JobListing | Notice` の判別共用体にする（`kind` で判別）。`toListing(row)` が種類ごとに必須項目を検査して変換する。

| 関数 | 内容 |
| --- | --- |
| `eventAvailability(e, now)` | `ended` → `deadline_passed`（application_deadline）→ `full`（remaining ≤ 0）→ `open` |
| `jobAvailability(j, now)` | `ended` → `deadline_passed` → `open`。募集人数に達しても締め切らない |
| `isHeadcountReached(j)` | `reserved_quantity >= headcount`。求人詳細の青い注意文に使う |
| `priceLabel(e)` | `price_per_person` が 0 か null なら「無料」、それ以外「500円」 |
| `payLabel(j)` | `pay_unit`＋`pay_amount` があれば「日給」「9,000円」、なければ `pay_text` だけ |
| `scheduleText(start, end, workText?)` | 求人で `work_text` があればそれ、なければ `formatPickup` と同じ規則 |

### 3.2 予約（`features/bookings`）

| 関数 | 内容 |
| --- | --- |
| `expiresAt(b)` | 2.2 の規則で期限切れになる時刻 |
| `effectiveStatus(b, now)` | `reserved` で `expiresAt <= now` なら `expired`、それ以外は DB の値 |
| `userStatusLabel(kind, status)` | README「状態と表示名」の利用者側。ただし下記の例外 |
| `numberLabel(kind)` | 予約番号／申し込み番号／受付番号 |
| `groupActive(bookings, now)` | U-22「予約・申し込み中」を日付で束ねる。日付＝開始日。ただし商品の受け取り期間がすでに始まっていれば今日。日付昇順、同じ日は開始時刻順 |
| `activeRowText(b, now)` | 行の 2 行目と 3 行目。商品：同日なら「11:30〜13:30」、複数日なら「〜10/12(月)」／場所＝店舗名。イベント：時間帯／場所＝place_name。求人：時間帯／「連絡をお待ちください」 |
| `historyLine(b)` | 履歴の 3 行目。受け取り済み「9/27(日) 受け取り」（イベント「参加」、求人「勤務」）、キャンセル「9/24(木) キャンセル」、期限切れ「受け取り期間 9/18(金) まで」（イベント「開催日 …」、求人「勤務日 …」） |
| `cancelState(b, now)` | `can`（期限内）／`deadline_passed`／`not_allowed`（期限なし）／`none`（予約中でない） |

**状態名の例外（判断）**：design 00 の Q11「イベント・求人は記録がないまま翌日になったら状態名そのまま履歴へ」に従い、イベント・求人の `expired` は利用者側では「申し込み済み」「応募済み」と表示する（灰ピル）。DATA_MODEL の状態遷移（expired にする）は運営側の表示のために残す。

### 4.9 登録情報の変更

- ナビ「登録情報」、入力 3 つ（お名前／電話番号＋補足「変更後の内容は、予約中の予約にも反映されます」／メールアドレス＋補足「ログインに使うため、変更すると新しいアドレスに確認リンクを送ります。リンクを押すと変更が完了します」）、下に主「保存する」
- 保存：名前・電話は `profiles` を即更新。メールが変わっていれば `updateUser` を呼び、完了後に青帯「確認リンクを送りました。新しいアドレスのリンクを押すと変更が完了します。」
- 変更がなければ保存ボタンを押せない

### 4.10 U-02 アカウント削除

- 開いた時点で自分の予約中を取得
- 予約中なし：見出し 20/900「アカウントを削除する前に\nご確認ください」→ 白カードに赤い「・」付きの注意 3 つ → 下に赤塗り「アカウントを削除する」→ 確認シート「本当に削除しますか？」「削除したアカウントは元に戻せません。」赤塗り「削除する」／副「やめる」→ RPC → サインアウト → ログイン画面へ（スタックを戻してから）
- 予約中あり：見出し「受け取り前の予約があるため、\n今は削除できません」→ 説明 14.5 → 白枠に予約の行（状態ピル、右に「予約番号 0427」、タイトル、日時と場所）→ 主「予約・申込を見る」、削除ボタンは無効色（`#EFE9DF` 地 `#9A9087` 字）
- RPC が `has_active_bookings` を返したら予約中ありの表示に切り替える

### 4.11 規約類（`legal/[doc]`）

`terms`／`privacy`／`tokushoho`／`contact`。ナビにタイトル、本文は「内容は準備中です。」。文面を受け取ったら差し替える。お問い合わせは文面確定後にメールアドレスか電話番号を出す。

### 4.12 スタッフメニュー入口（`staff/index`）

ナビ「スタッフメニュー」と空状態「運営画面は準備中です」。A-01 の実装時に置き換える。

- 純関数：`effectiveStatus`・`expiresAt`（商品の pickup_end、イベントの翌日 0:00 JST の境界）、`groupActive`（受け取り中の複数日は今日に入る）、`historyLine`、`cancelState`、`eventAvailability`・`jobAvailability`、`priceLabel`・`payLabel`、お知らせの未読判定

## 7. 実装で変えた点・残った点

### 変えた点

| 項目 | 設計時 | 実装 | 理由 |
| --- | --- | --- | --- |
| 申し込み画面 | 種類ごとの画面 | 共通の `BookForm` と種類ごとの仕様 `bookSpec()` | 骨格が同じで、違いは文言・上限・確認表だけだった |
| 詳細のカード | 商品専用の `ProductInfoCards` | 汎用の `ScheduleCard`／`TermsCard`／`PaymentItem`（`DetailCards.tsx`） | 商品・イベント・求人で同じ見た目を使い回すため |
| 掲載の型 | 商品だけ | `Listing = Product \| EventListing \| JobListing \| Notice` | 詳細・申し込みの入口で種類を判別する |
| シードの売り切れ確認用 | 受け取りが今日 | 受け取りが明日 | 期限切れ処理で枠が戻り、売り切れでなくなるため |
| AsyncStorage のテスト用モック | テストごと | `src/test/setup.ts` で共通化 | 書き漏れでテストが落ちるため |

### 確認済み
