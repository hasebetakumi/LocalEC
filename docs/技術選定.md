# 技術選定

iOS・Androidアプリとして開発する前提で、生成AIを活用した少人数開発に最適な構成を定める。

## 結論

**Expo（React Native）+ TypeScript + Supabase** を採用する。

## 選定基準

- **生成AIが得意な言語**：TypeScript／React系は事例が最も多く、AIの出力精度が高い
- **全体を1言語に統一**：アプリ・管理画面・バックエンドを同じ言語にし、AIに一気通貫で変更を任せられる
- **型とテストで守る**：AIの生成コードの誤りを型チェックとCIで機械的に弾く
- **枯れた技術**：情報が多く、AIの知識が追いつく技術を選ぶ

## 構成

| 層 | 採用技術 | 理由 |
| --- | --- | --- |
| アプリ | Expo（React Native）+ TypeScript | 1コードでiOS・Android・Web版を出せる |
| 管理画面 | Next.js または Expo Web | 運営側の掲載入力用。型定義をアプリと共有 |
| バックエンド | Supabase（DB・認証・ストレージ） | サーバー構築不要で実費が小さい。地域ごとのデータ分離で横展開に対応 |
| 通知 | Expo Notifications | 新着お得情報・フォロー店舗の投稿を配信 |
| 決済（フェーズ2） | Stripe | 実物商品のためストア課金の対象外 |
| 配信 | EAS Build／EAS Update | 軽微な修正はストア審査なしで配信 |

Web版も同時に出せるため、SEO対策やLINEからのリンク共有にそのまま使える。

## 決済とストア規約

| 売るもの | 例 | 決済手段 |
| --- | --- | --- |
| デジタル商品 | Spotifyの有料プラン、有料機能 | ストア課金が必須（手数料15〜30%） |
| 実物商品・サービス | 弁当・米・野菜の予約購入 | Stripeなど外部決済を使う（手数料3.6%前後） |

- 生活者の商品購入は実物商品なのでStripeで問題ない。Uber EatsやAmazonと同じ扱い
- アプリ内で決済を完結できる。StripeのPayment Sheetで、カード・Apple Pay・Google Payをその場で支払える
- 事業者の月額や掲載料はデジタルサービス扱いになるため、アプリには載せずWeb管理画面や請求書で処理する

## 代替案と不採用の理由

- **Flutter + Firebase**：UI品質は高いが、Web版・SEOが弱く、管理画面が別言語になる
- **Swift／Kotlin（ネイティブ）**：コードが2つになり、この規模では維持コストが見合わない

## 開発の進め方

- モノレポでアプリ・管理画面・バックエンドの型定義を共有する
- リポジトリに開発ルールを置き、AIに毎回読ませる
- 型チェック・Lint・テストをCIで必ず通す
- Supabase・Expo・Stripeはいずれも無料枠から始め、初期費用ゼロの方針と揃える
